# Failbook — 研究、内容与验收 brief

配合根目录 [AGENTS.md](../AGENTS.md) 使用。初次资料核对：2026-11-03。当前没有已经发布的案例集、评测结果或排名。

## 要解决的任务与核心亮点

开发者需要知道某个 AI 失败能否复现、失败发生在哪里、修复后是否真的通过。建议优先验证“失败到修复的证据链”：每个案例附可运行输入、验收方法、原始失败与后续复测，所有结论可回到证据。

首版限定一个领域，先完成少量扎实案例，再扩展到约 10–20 个。案例质量、失败分类与复现成本优先于数量和排行榜。

## 技术探索应回答什么

1. 评估复用 Inspect 等现有框架，先把任务、执行、评分、运行记录分开，不先开发另一套通用评测平台。
2. 验收依据最终文件、程序行为与必要外部状态；仅日志出现“已运行”或模型自述“完成”不足以通过。正确答案、已知失败和边界样例都应验证评分器。
3. 确定性检查优先；语义评价需要 rubric、评分模型版本、样本校准及分歧处理，显示人类/模型/规则各自的判定。
4. 记录模型完整标识、工具/Agent 版本、任务与输入哈希、配置、时间、调用预算及环境。外部服务变化、随机性和数据污染影响可重复性，不能声称完全确定。
5. 运行记录追加保存；重试、超时和基础设施错误都要保留。比较时说明同等预算或差异；真实成本、延迟和样本数与通过率同时呈现。
6. 不执行未知案例附带的任意脚本。使用隔离环境、最小权限和网络/时间/资源限制，避免评测产生真实发送、付款或破坏性行为。

## 优秀参考与转化方向

已核对的一手入口如下；方法借鉴不表示本项目已达到它们的规模或效度。正式使用数据或代码前核实版本、许可及任务适配性。

| 参考 | 类型与用途 | 建议借鉴及边界 |
| --- | --- | --- |
| [Inspect](https://inspect.aisi.org.uk/) | UK AI Security Institute 与 Meridian Labs 的评测框架 | 研究任务、工具、评分和隔离执行的组合；尽量复用，保留轻量案例格式。 |
| [Inspect Log Viewer](https://inspect.aisi.org.uk/log-viewer.html) | 官方结果审阅界面 | 借鉴从汇总钻取消息、评分和元数据；读者应能检查证据而不只看到一个分数。 |
| [SWE-bench](https://www.swebench.com/) | 软件工程评测及官方结果展示 | 研究可执行验收和结果口径；它的任务域与成功率不能外推到本案例集。 |
| [ProgramBench](https://programbench.com/) | 2026 软件重建评测及官方结果 | 借鉴最终行为验收与成本并列；测试不能穷尽行为，不能把高测试通过率写成绝对正确。 |
| [Datasheets for Datasets](https://arxiv.org/abs/1803.09010) | 数据集说明方法论文，2021 修订版 | 借鉴来源、构成、用途与限制的记录；这是经典方法参考，不称最新论文。 |
| [Apple Design Awards 2026：Tide Guide](https://www.apple.com/newsroom/2026/06/apple-reveals-winners-of-the-2026-apple-design-awards/) | Visuals and Graphics 类应用获奖作品 | 研究专业数据如何清晰呈现；本项目应突出样本数、条件和不确定性，不借用其主题皮肤。 |

## 案例与内容的最低结构

每个案例至少包含：稳定 ID 与版本、简明标题、用户任务、输入来源及许可、环境与运行方法、验收规则、预期结果、观察到的结果、证据位置、失败类别、限制，以及修复/复测记录。失败类别允许“尚未确定”。

- 标题描述可观察失败，例如“修改表格数据后，总计未更新”，避免“某模型彻底不行”等煽动性概括。
- 原始结果、解释和建议分栏；一条案例失败只能支持该条件下的结论。
- 精选失败案例存在选择偏差；没有定义样本总体与抽样方式，不发布暗示总体可靠性的胜率榜。
- 小样本直接显示计数；不制造精确小数、假置信区间或未经校准的综合分。重复运行应保留分布，不能只挑最好/最坏的一次。

## 界面与首版验收

界面优先是可检索的案例目录＋证据审阅页。比较“研究档案”和“调试工作台”两个方向，选择能最快理解任务、复现和检查证据的方案。避免将案例变成缺乏上下文的排行榜卡片。

| 检查 | 最小证据 |
| --- | --- |
| 案例完整 | 输入与许可、版本、验收、预期/实测、证据全部齐全；路径可解析，不能链接到开发者私有目录。 |
| 评分器有效 | 已知正确样例通过、已知失败样例失败；环境故障与任务失败分开，空输出不会误判通过。 |
| 可复现 | 从干净环境按说明复现至少一个失败并执行修复后的回归；不能复现的记录条件和限制。 |
| 记录可信 | 重跑追加新 run，不覆盖原始证据；脱敏后重新核对，敏感数据不进入公开仓库。 |
| 报告清晰 | 从结果能回到案例、运行条件与原始产物；导出后仍可理解，成本缺失明确显示未知。 |

代表性演示：读懂一个失败 → 执行可复现任务 → 查看确凿证据 → 应用修复 → 对照新运行结果。不要用纯文字编造一个“翻车故事”充当可复现案例。
